## 1. 가오픈이란 무엇인가

**사업자등록증·통신판매업 등록증을 붙이고 결제·로그인 모듈을 얹기 직전까지 전부 완성된 상태.**
그 전에는 뿌리기(확산)로 넘어가지 않는다.

**근거**: 이 정의와 필수 요건 여섯은 **2026-09-09 이 회차(R1) 지시문에서 처음 나왔다.**
`HANDOFF-v2.md`·`docs/현황.md`를 grep해도 "가오픈"·"사업자"·"통신판매업"이라는 말 자체가
이전에 없었다(§8.6의 "광고 사업자에게"는 무관한 문맥). **추측이 아니라 이번에 새로 확정된
기준**이라는 뜻이므로, 옛 문서가 이 항목들에 대해 뭐라고 적었든 이 절이 우선한다.

| 묶음 | 내용 | 상태 | 비고 |
|---|---|---|---|
| **A. 콘텐츠 마무리** | ~~신강신약 조각 얹기~~ **완료(A1·A2)** / 태어난 시간 추정(**진단 A3 · 설계 A4 완료 → 구현 A5가 다음**) / 밀린 눈 확인 5건과 그 수정 | **지금 여기 — 다음은 A5(화면 구현)** | 지금 구조(서버 없는 단일 HTML) 그대로 가능 |
| **B. 계정·서버 기반** | 코드 교환 / 연동 목록·끊기 / 그룹 초대 / 로그인 | **미착수 — 설계부터 필요** | 지금은 서버 없는 단일 HTML이다. **가장 큰 덩어리** |
| **C. 사업자등록 · 통신판매업** | Teo 몫 | 근거 없음(확인 필요) | 서류 대기 시간이 있으니 **A와 병행 시작** 권장 |
| **D. 결제 모듈 → 가오픈 → 뿌리기** | | 미착수 | B가 끝나야 착수 가능(결제도 로그인 위에 얹힌다) |

**순서가 왜 이런가** — A는 지금 구조로 되는 일이라 계속 진행한다. B는 "서버+로그인"이 선행이라고
§8.1·§8.2가 이미 못박아 뒀다(2026-08-28 결정, 아래 §6 회차 이력 참고). C는 A·B와 무관한
행정 절차라 병행 가능하다. D는 B 없이 성립하지 않는다(결제는 계정에 귀속되는 기능이라 로그인이
먼저 있어야 한다).

### 묶음 B의 밑그림 — 이미 정해진 것

서버·계정을 새로 설계할 때 처음부터 다시 생각할 필요가 없는 부분이 `HANDOFF-v2.md` §7·§8에
이미 있다. 다음 회차가 그대로 이어받을 수 있게 옮겨 둔다.

- **인물 ≠ 계정** (§7.1) — 지금 등록한 사람은 비회원 "인물 노드"다. 나중에 가입하면 자기 노드를
  "클레임"한다. **이 분리가 코드 교환·연동의 전제**다.
- **스키마 선반영이 미완이다** — §7.3이 "노드 스키마에 `claimedBy`, `visibility` 필드를 미리
  넣어 두라"고 했지만, **실제로는 안 들어가 있다**(`grep -a 'claimedBy\|visibility' index.html`
  — CSS `visibility` 속성 3건만 나오고 스키마 필드는 0건, 2026-09-09 R1 실측). 지금 저장 구조
  변경분(§7.3 "설계 단계에서 반영, 나중에 붙이지 말 것")을 이때 함께 넣어야 한다.
- **토큰 경제(§8.1)** — 무료 3명분 지급, 등록 1명분 소모, 그룹 생성은 무제한(비용이 안 든다).
  건별 원장 방식(잔액만 두지 않는다) — 나중에 대시보드·환불 규정을 붙일 때 과거 기록이 있어야
  한다. **지금 되는가 — 아니오.** 서버 없이는 잔액 조작을 막을 수 없다(브라우저 저장을 지우고
  다시 시작하면 무료분을 계속 받는다).
- **QR·전화번호 연결(§8.2)** — 실제 만났을 때 QR로 대면 등록(토큰 없이). 전화번호는 선택 항목
  (강제하면 포기율이 올라간다). "누가 나를 등록했다"는 미가입자에게 알리지 않는다(스팸이 된다) —
  본인이 가입한 시점에만 알린다.
