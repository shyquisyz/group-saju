**3번 사전 확인(코드 실측)** — 높이를 재는 시점과 고정:

| 항목 | 현재 코드 |

| 문서 스크롤 되돌림 | 없음 |

|---|---|---|---|

## 2. PC 공유하기 / 이미지로 저장 역할 분리

| 버튼(PC) | 전(3d) | **후(3e)** | 실제 클릭 결과(로컬, Windows 10·Chrome 152) |
|---|---|---|---|
| 공유하기 | 문구+링크 복사 + PNG 저장 | **이미지만 클립보드**(`ClipboardItem image/png`), 저장 없음, 문구 "이미지가 복사됐어요 — 카톡 PC 등에 Ctrl+V" | 클립보드에 **1080×1350 이미지**(PowerShell로 읽음), 텍스트 0자, `cardDownload` 호출 **0** |
| 문구 복사(새 버튼, PC만 표시) | 없음 | 카드 설명 한 문장 + 링크를 **텍스트만** 복사, 문구 "문구를 복사했어요 — 붙여넣으세요." | 클립보드 텍스트 95자(주소·「사주은하」 포함), 이미지 **없음** — 둘이 섞이지 않음 |

- 모바일 경로 무변경(`isDesktopPC()`가 false면 종전 분기). 3d의 옛 PC 분기는 `else if(false)`로 남겨 정정 기록으로 둠.
- **못 한 것**: 저장의 "파일이 실제로 생김"은 이 PC의 크롬이 **다운로드마다 '다른 이름으로 저장' 창을 띄우는 설정**

## 3. 아이폰 첫 진입 하단 빈 공간 — 방어 조치 적용, 원인은 미확정

적용(a·b·c 전부):
- **a. 재동기** `viewportResync(why)`: `--vvh` 갱신 → **문서가 스크롤돼 있으면 `scrollTo(0,0)`** → `resize()`(캔버스) → `syncChromeMetrics()`(태그바·헤더).
  호출: `load` 직후 · `requestAnimationFrame` 한 번 더 · 300ms · 1000ms · `visualViewport resize/scroll` · `orientationchange`(+300ms).
- **b.** `html,body{overscroll-behavior:none}` 추가(overflow hidden·height 100%는 이미 있었다). **첫 화면 카드의 `100vh`·`64vh`를
  `var(--vvh, 100vh)` 기준으로 정정** — 문서가 보이는 높이보다 길어질 수 있는 유일한 요소였다. 기존 스크롤 잠금
  (`#panel,.sheet,.obcard{overscroll-behavior:contain}`)과 충돌 없음(패널 안 스크롤은 그대로).
- **c.** `?debug=1`이면 왼쪽 위에 `innerH / vvH / vvTop / scrollY / canvasH / tagbar↓ / 마지막 재동기 이유`를 0.5초마다 표시.
  코드에 `TODO[뿌리기 전 제거]` 표시.

**실측(로컬 크롬, 1279 높이)**: 표시 내용 `innerH 1279 · vvH 1279 · vvTop 0 · scrollY 0 · canvasH 1279 · tagbar↓ 1279 · last:1000ms`,
`.obcard` max-height 1223(= 1279 − 56, `--vvh` 반영), body overscroll `none`, 자가진단 56/56. 데스크톱에서는 변화 없이 그대로다.

**원인 추정(확정 아님)**: 첫 진입 = 첫 화면 카드가 떠 있는 상태. iOS에서 카드가 `100vh − 56`까지 커져 보이는 영역보다 길어지면
사파리가 문서 전체를 툴바 높이만큼 스크롤할 수 있고, 고정 요소(헤더·캔버스·태그바)가 함께 위로 밀려 아래에 바탕색이 남는다.
새로고침하면 카드가 접힌 상태거나 툴바 상태가 달라 사라진다. 사용자 관찰(제목 위로 밀림 + 아랫변이 툴바 위 ~160px)과 맞는다.
b의 `--vvh` 정정과 a의 `scrollTo(0,0)`가 각각 이 가설의 원인과 증상을 막는다.
