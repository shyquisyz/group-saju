## 3. 구현 중 실측으로 잡은 것 — `PERSON_ITEM_NAMES` 인덱스 어긋남

A4 설계 문서는 `personReading()`이 **여덟 항목**이던 2026-09-09에 우선순위 표를 만들었다.
그런데 A5 착수 시점(2026-09-17)에는 **A6-3이 이미 "자리마다 놓인 기운"을 ④·⑤ 사이에 끼워
넣어 아홉 항목**이 돼 있었다(`docs/reports/2026-09-17-A6-3-치환2.md`). 설계 문서만 보고
`PERSON_ITEM_NAMES`를 옛 여덟 개로 그대로 옮겨 적었더니:

```
실측(브라우저) — "아침" 선택 후 2번째 질문:
  itemName 표시: "어울리는 일"
  실제로 보여준 문장: "눈치보다 재주가 먼저 크는 쪽으로 출발했습니다…" (← 자리마다 놓인 기운의 문장)
```

**분기표 발동** — "지시(설계 문서)가 전제한 것을 코드에서 실제로 확인한다"(CLAUDE.md 착수 전
점검). 설계 문서 작성 시점과 지금 코드 사이에 A6-3이 껴 있다는 것을 놓쳤던 것이라, 문서가
틀린 게 아니라 **문서 이후의 변경을 반영 안 한 것**이었다.

**고침**: `PERSON_ITEM_NAMES`에 "자리마다 놓인 기운"을 인덱스 4에 끼워 아홉 개로,
`EST_ITEM_PRIORITY`도 자시 판별용 셋(0·4·7)을 앞에 두도록 다시 짰다(자리마다 놓인 기운도
일주 자체로 정해지는 항목이라 0·7과 같은 급으로 올렸다 — 근거는 코드 주석에 남겼다).

**재발 방지**: `personItemAlign` 자가진단을 추가했다 — `personReading()`을 실제로 불러
`.h` 순서와 `PERSON_ITEM_NAMES`를 대조한다. personReading 항목이 다시 늘거나 줄면 이
테스트가 실패로 알려준다.

— 사용자의 실제 저장본이 있는 채로 sajuSelfTest를 돌리면 안 되는 부작용이 생긴다. 저장·지우기
왕복은 아래 §5(브라우저 실측)로 대신한다.

## 5. 브라우저 실측

### 5-1. 흐름 · 항목 정합
- "아침" 선택 → 2문항 만에 단일 승자(묘시). 두 질문 모두 실제 `personReading` 문장이 나왔고
  `itemName`과 내용이 일치했다(§3 고침 이후 재확인).
- "밤" 선택 → 2문항 뒤 자시(23시대) vs 해시가 동점 → 직접 고르기 화면 정상 표시 → 자시 선택 →
  결과 화면에 "추정" 배지 + "자시(23–01시) · 밤 11시대쯤" 정상 표시.

### 5-2. 저장 · 지우기 · 새로고침 (demoMode를 실제로 끄고 진행)
```
온보딩 완료(demoMode:false) → localStorage.getItem('groupsaju:save') 있음
추정 저장 → n.birth.est(메모리) === 저장본의 birth.est(JSON.parse) — 완전 일치
저장본 v: 3
페이지 새로고침(location.reload) → n.birth.est 그대로 유지 — 재기동 시 마이그레이션·복원 정상
추정 지우기(confirm 예) → n.birth.est === null, 저장본도 null, 버튼이 "추정해 보기 →"로 복귀
```

### 5-3. 이름만 고쳐 저장해도 추정값이 살아남는가 (§2 savePerson 고침 확인)
```
추정 저장 → 정보 수정 시트 열기(openAddSheet) → 이름 그대로 저장(addbtn 클릭)
→ n.birth.est 그대로(고침 전과 문자 단위 동일)
```
고치기 전이었다면(carry-over 없이) 이 시점에 `null`이 됐을 자리다.
